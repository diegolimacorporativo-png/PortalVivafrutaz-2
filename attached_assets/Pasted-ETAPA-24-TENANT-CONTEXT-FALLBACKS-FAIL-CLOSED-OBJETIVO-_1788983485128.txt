ETAPA 24 — TENANT CONTEXT / FALLBACKS / FAIL-CLOSED

OBJETIVO:
Auditar profundamente o mecanismo central de resolução de tenant e identificar qualquer situação em que uma rota tenant-bound possa cair acidentalmente em comportamento GLOBAL quando empresa/tenant não estiver resolvido.

Esta etapa é de segurança multi-tenant.

IMPORTANTE:
Não fazer refatoração geral.
Não alterar regras de negócio sem evidência.
Não mexer em módulos já corrigidos, exceto quando for necessário corrigir um fallback central comprovadamente inseguro.

NÃO mexer em:
- NF-e
- fiscal
- certificado A1
- impostos
- DANFE
- GPS/Android Tracker
- Push
- financeiro/banco
- inventário
- products/prices
- deliveries
- route stops
- quotations
- incidents

Não criar migration.
Não alterar schema.
Não alterar dados reais.
Não fazer operações destrutivas.
Não fazer commit.

==================================================

Inspecionar:

- server/core/tenant/context.ts

- session.user.empresaId

Mapear exatamente a prioridade usada para resolver o tenant.

4. quando pode ficar null/undefined;
5. o que acontece quando fica null/undefined.

==================================================
2. PROBLEMA PRINCIPAL — FALLBACK GLOBAL
==================================================

Pesquisar por padrões como:

if (!empresaId)
if (!tenantId)
empresaId ? ...
empresaId ?? ...
empresaId || ...
tenantId ?? ...
tenantId || ...

e principalmente consultas como:

WHERE empresa_id = ${empresaId}

ou lógica equivalente onde:

empresaId == null

pode resultar em:

- buscar todos;
- buscar registros globais;
- remover filtro de empresa;
- executar operação sem escopo.

Também pesquisar repositories/storage que tenham comportamento semelhante a:

if (empresaId) {
  filtrar por empresa
} else {
  retornar tudo
}

Esse comportamento pode ser legítimo para ferramentas globais.

O objetivo é descobrir onde ele é perigoso em endpoint tenant-bound.

==================================================
3. SEPARAR GLOBAL LEGÍTIMO DE FALLBACK PERIGOSO
==================================================

NÃO remover global fallback indiscriminadamente.

Classificar cada ocorrência como:

A) GLOBAL LEGÍTIMO
Exemplo:
MASTER/DIRECTOR sem empresa em ferramenta administrativa global.

B) TENANT-BOUND
Precisa obrigatoriamente de empresa.

C) OPERAÇÃO MISTA
Pode trabalhar globalmente ou tenant-bound dependendo do usuário/política.

D) PÚBLICO
Não possui tenant.

E) SUSPEITO
Não está claro por que fica global quando empresa não está resolvida.

Somente corrigir B/E e D quando houver risco real.

==================================================
4. REGRAS OBRIGATÓRIAS
==================================================

Para endpoint TENANT-BOUND:

Se sessão não possui tenant resolvido:

-> FAIL CLOSED

Preferencialmente:

403

ou 401 quando o problema for ausência de autenticação.

Nunca:

-> executar consulta global silenciosamente.

Para endpoint GLOBAL legítimo:

MASTER/DIRECTOR sem empresa podem continuar globais conforme política existente.

ADMIN/DEVELOPER sem empresa:

não devem automaticamente ganhar acesso global.

Preservar as regras já estabelecidas nas etapas anteriores.

==================================================
5. ATENÇÃO AO tenantId ALTERNATIVO
==================================================

A auditoria anterior encontrou `?tenantId` em:

server/core/tenant/context.ts

Investigar cuidadosamente.

Descobrir:

- quem pode enviar esse parâmetro;
- se ele tem prioridade sobre session.companyId/session.user.empresaId;
- se um usuário tenant-bound consegue trocar de tenant;
- se X-Empresa-Id pode fazer o mesmo;
- se query/body/header pode sobrescrever tenant confiável.

REGRA:

Para usuário tenant-bound:

sessão deve vencer qualquer tenant fornecido pelo cliente.

Exemplo:

sessão = empresa 10
cliente envia:
?tenantId=20

Resultado obrigatório:

tenant 10

ou requisição rejeitada.

Nunca tenant 20.

Para usuários globais que legitimamente podem selecionar empresa:

preservar o mecanismo existente, mas exigir autorização apropriada.
