CORREÇÃO 6 — ISOLAMENTO MULTI-TENANT DO EMPRESA-CONFIG

Quero corrigir APENAS o risco de IDOR/autorização identificado no módulo de configuração de empresa.

Arquivo principal identificado na auditoria:

server/routes/empresa-config.routes.ts

Endpoints:

GET /api/empresa-config/:empresaId
PUT /api/empresa-config/:empresaId

PROBLEMA IDENTIFICADO:

As rotas verificam roles administrativas, porém não garantem de forma consistente que um usuário administrativo tenant-bound esteja acessando somente a própria empresa.

Isso pode permitir:

empresa A → informar empresaId B → consultar ou alterar configuração da empresa B.

OBJETIVO:

Garantir isolamento completo por tenant nesse módulo, preservando o acesso global legítimo.

1. NÃO tocar em NF-e.

2. NÃO alterar schema.

3. NÃO criar migration.

4. NÃO alterar dados existentes.

5. NÃO alterar valores/configurações existentes.

6. NÃO fazer refatoração ampla.

7. Corrigir somente autorização e isolamento multiempresa.

REGRA TENANT-BOUND:

Se a sessão possui empresaId/tenant:

O parâmetro:

/api/empresa-config/:empresaId

DEVE corresponder ao tenant da sessão.

Exemplo:

sessão → empresa A

GET /api/empresa-config/A
→ permitido.

GET /api/empresa-config/B
→ bloqueado, preferencialmente 404.

PUT /api/empresa-config/B
→ bloqueado.

Nunca confiar apenas no empresaId da URL.

O tenant deve ser derivado da sessão/contexto autenticado.

USUÁRIOS GLOBAIS:

Identifique quais roles são realmente globais no projeto.

Somente usuários explicitamente globais podem acessar configurações de outros tenants.

Não transformar ADMIN tenant-bound em global automaticamente.

Se um usuário tiver role administrativa mas possuir empresaId na sessão:

→ ele continua tenant-bound.

Se houver usuário global sem tenant:

→ preservar somente o comportamento global legítimo já existente.

NÃO inventar novas roles globais.

GET:

Garantir:

id da URL + tenant da sessão

para usuários tenant-bound.

PUT:

Garantir:

id da URL + tenant da sessão

antes de qualquer alteração.

A validação deve acontecer ANTES de executar update.

Não fazer:

1. buscar por ID global;
2. alterar;
3. verificar tenant depois.

O ownership deve fazer parte da própria operação/consulta sempre que possível.

SE O REPOSITÓRIO PERMITIR:

Preferir condição equivalente a:

WHERE empresa_id = tenantId

e:

WHERE id = empresaId
AND empresa_id = tenantId

conforme a estrutura real.

CUIDADO COM CAMPOS DE TENANT:

Se PUT aceitar qualquer campo como:

- empresaId
- empresa_id
- companyId

não permitir que um tenant-bound altere o tenant da configuração.

Não permitir mover configuração de uma empresa para outra.
