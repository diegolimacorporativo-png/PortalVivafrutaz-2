2. SEPARAR OS FLUXOS

Classificar cada endpoint em:

A) CONFIGURAÇÃO ADMINISTRATIVA
Exemplo:
- VAPID/public configuration
- configuração global
- habilitar/desabilitar Push

B) SUBSCRIPTION DO USUÁRIO
Exemplo:
- registrar subscription
- remover subscription
- atualizar subscription

C) TESTE DE PUSH
Exemplo:
- enviar uma notificação de teste

D) ENVIO OPERACIONAL
Exemplo:
- disparar notificação para usuários/empresas

Cada categoria deve ter sua própria autorização apropriada.

3. PROBLEMA PRINCIPAL

Verificar se um usuário autenticado consegue:

- consultar configuração global indevida;
- alterar configuração de Push;
- enviar Push para usuários de outra empresa;
- testar Push em outro tenant;
- registrar subscription vinculada a outra empresa;
- remover subscription de outro usuário;
- escolher companyId/empresaId/tenantId pelo body;
- escolher recipient/userId arbitrariamente;
- acessar tokens/subscriptions de terceiros.

Qualquer `companyId`, `empresaId` ou `tenantId` enviado pelo cliente NÃO deve ampliar o escopo do usuário.

4. RBAC

Aplicar RBAC compatível com a arquitetura atual.

Para configurações administrativas sensíveis:

- MASTER
- ADMIN/DIRECTOR conforme política administrativa existente
- DEVELOPER somente se a política existente realmente permitir

Não transformar automaticamente todo ADMIN/DEVELOPER em acesso global.

Usuário tenant-bound:
- somente própria empresa.

Usuários operacionais:
- não ganhar acesso administrativo apenas por possuir role operacional.

CLIENT:
- somente seus próprios fluxos de subscription, se existentes.

DRIVER/MOTORISTA:
- somente seu próprio fluxo, se existir.

Para teste administrativo de Push:
- não permitir que CLIENT, DRIVER, MOTORISTA ou perfis operacionais enviem notificações arbitrárias.

5. SUBSCRIPTIONS

Auditar a entidade/tabela utilizada para armazenar subscriptions.

Descobrir como ela identifica:

- usuário
- empresa
- endpoint
- subscription
- dispositivo, se houver

Não criar tabela nova nesta etapa.

Na criação/atualização:

- userId deve vir da sessão quando o fluxo for "minha subscription";
- empresa deve ser derivada do usuário/tenant;
- não confiar em `userId`, `companyId`, `empresaId` ou `tenantId` enviados pelo cliente.

Na remoção:

- usuário comum somente sua própria subscription;
- administrador tenant-bound somente conforme escopo permitido;
- cross-tenant bloqueado.

6. ENDPOINT DE TESTE

Se existir algo como:

POST /api/push/test

ou equivalente:

proteger explicitamente.

O cliente não deve conseguir escolher livremente:

- recipientUserId
- userId
- companyId
- empresaId
- tenantId
- subscription endpoint
- payload arbitrário perigoso

Validar o destinatário no servidor.

Se for uma ferramenta administrativa de teste:

- exigir RBAC adequado;
- validar tenant;
- impedir cross-tenant acidental.

NÃO enviar Push real durante os testes.

Use mocks/stubs.

9. TENANT ISOLATION

Testar:

Tenant A:
- registra subscription própria;
- acessa própria subscription/configuração permitida.

Tenant B:
- não consegue acessar/remover subscription de A;
- não consegue enviar Push para A;
- não consegue usar companyId de A para ampliar escopo.

MASTER/DIRECTOR:
- manter comportamento global legítimo conforme política existente.

ADMIN/DEVELOPER vinculados:
- permanecer tenant-bound.

Usuário sem empresa:
- fail closed quando o endpoint exige tenant.

10. TESTES

Criar testes direcionados cobrindo:

- 401 sem sessão;
- 403 role não permitida;
- MASTER permitido onde aplicável;
- ADMIN permitido onde aplicável;
- DIRECTOR permitido onde aplicável;
